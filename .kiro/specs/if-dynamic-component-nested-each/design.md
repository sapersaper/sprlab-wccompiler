# Design: if + `<component :is>` inside nested forEach

## Current Architecture

### tree-walker flow (`walkBranch`)

```
1. processForBlocks       → finds each directives, replaces with <!-- each -->
2. processIfChains        → finds if/else chains, replaces with <!-- if -->
3. processDynamicComponents → finds <component :is>, replaces with <!-- dynamic -->
4. walkTree               → extracts bindings, events, slots from remaining DOM
```

### Codegen flow (`generateItemSetup`)

```
For each forBlock item:
  1. Generate bindings (text), events, show, attr, model
  2. Generate ifBlocks (line 730): inline conditional rendering with branch templates
  3. Generate nested forBlocks (line 865): inline forEach with bindings + events
  4. Generate dynamicComponents (line ~940): inline document.createElement
```

### The Problem

When `if` wraps `<component>` inside a forEach template:

```
template HTML: "<div if='cond'><component :is='x'/></div><div else>...</div>"
```

1. `processIfChains` finds the if/else, creates an ifBlock. Calls `buildIfBlock` → `walkBranch` on each branch.
2. Branch 0's `walkBranch` finds the `<component>` and extracts it via `processDynamicComponents`.
3. Result: `ifBlock.branches[0].dynamicComponents = [{...}]` ← CORRECT!
4. `processIfChains` replaces if/else with `<!-- if -->` in the main DOM.
5. `processDynamicComponents` on the main DOM finds nothing (component was removed in step 4).
6. Codegen for the forEach item needs to generate the ifBlock AND its dynamic components.
7. Codegen for nested forEach (line 865+) generates inline simple code — no ifBlocks.

So the data is CORRECT (the ifBlock has the dynamic component), but the codegen doesn't
generate it for nested forEach items.

## Proposed Solution

### Step 1: Make nested forEach codegen call `generateItemSetup` recursively

Instead of duplicating bindings/events/dynamicComponents inline, make both the if-branch
nested forEach and the direct nested forEach call `generateItemSetup` recursively.

The key fix: use `node` as the cloned element variable name (matching what `generateItemSetup`
expects via `pathExpr(path, 'node')`). This is safe because `const` is block-scoped —
each forEach callback creates its own scope.

```js
// Before (inline):
__for0_iter.forEach((subItem) => {
    const clone = document.createElement('template');
    clone.innerHTML = `...`;
    const innerNode = clone.content.firstChild;
    // Manual bindings, events...
    __anchor.parentNode.insertBefore(innerNode, __anchor);
});

// After (recursive):
__for0_iter.forEach((subItem) => {
    const clone = document.createElement('template');
    clone.innerHTML = `...`;
    const node = clone.content.firstChild;  // ← use 'node', not 'innerNode'
    generateItemSetup(lines, innerFor, itemVar, indexVar, ..., indentOverride);
    __anchor.parentNode.insertBefore(node, __anchor);
});
```

### Step 2: Fix anchor path recalculation for nested if-blocks

When `walkBranch` processes a branch's HTML, it wraps it in a `<div id="__branchRoot">`.
The childNode paths generated by `processIfChains` include this wrapper in the first segment.

`stripFirstAnchorSegment` removes the first segment for forBlocks and dynamicComponents.
But for if-blocks, the anchor path recalculation happens differently via `recomputeAnchorPath`.

The issue: when the forEach template is cloned (via `clone.content.firstChild`), the childNode
indices in the cloned DOM should match the original. But the cloned node's childNodes might
have different whitespace handling depending on the HTML parser.

**Solution**: Add a `stripFirstAnchorSegment` call for if-block anchors when they are
inside templates processed by `walkBranch`. This ensures the first segment (which corresponds
to the `__branchRoot` wrapper) is removed.

### Step 3: Ensure `generateItemSetup` indent handling

`generateItemSetup` has an `indentOverride` parameter (added in Phase 4). When called
recursively, the indent should be increased by 2 or 4 spaces to match the nesting level.

For if-branch nested forEach: `indent + '    '` (4 extra spaces)
For direct nested forEach: `indent + '  '` (2 extra spaces)

## Alternative Considered

### Keep inline codegen and add ifBlock generation manually

Rejected: leads to massive code duplication. The ifBlock generation code is ~70 lines
with template creation, condition evaluation, branch insertion, and dynamic component
handling. Duplicating this for nested contexts is too error-prone.

### Call `generateItemSetup` but exclude ifBlocks from nested calls

Rejected: ifBlocks are exactly what we need to generate. Excluding them defeats the purpose.

## Risks

- **Anchor path mismatch**: The cloned template may have different childNode counts
  than the temporary DOM used by `walkBranch`. Mitigation: test with JSDOM to verify
  the paths match.

- **Variable name collision**: Using `node` in nested scopes could shadow outer `node`.
  Mitigation: `const` is block-scoped; each forEach callback creates its own scope.
  JavaScript guarantees the outer `node` is restored after the callback returns.

- **Deep nesting performance**: Recursive `generateItemSetup` may increase compile time
  for deeply nested structures. Mitigation: deep nesting is rare; the current approach
  of full re-render (`__renderEach_0`) dominates runtime performance, not compile time.
